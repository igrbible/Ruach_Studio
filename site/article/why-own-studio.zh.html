为什么是我们自己的工作室，而不是一套 ComfyUI 插件

Viktor Zhuromskyy，鲁阿赫工作室（Ruach Studio）作者 · 2026 年 11 月 13 日。本文表明的是一种立场，而且是我自己的立场。它所依据的每一条事实都附有链接，好让你逐一核实。

和我们一起做歌的人里，有很多是从 ComfyUI 过来的。在那里，一个专业工作流要花好几周才能搭好，而下一次核心或节点更新就可能把它弄坏。留下的是一堆私有分叉，其中的修复太多时候再也没有回到上游。我管这叫 forkblow：分叉出去、私下打补丁、从不送回上游。鲁阿赫工作室走的是另一条路：一个页面上的八个房间，一个由我们亲手打补丁的音乐引擎，每个模型都固定归属于一个房间。为什么这样做、代价是什么、我们在哪些地方仍与 ComfyUI 有交集，还有我写给 ComfyUI 社区的告别信，都在下面。

总有人问我，为什么不干脆发布一个 ComfyUI 节点包。和我们一起做歌的人里，有很多是从 ComfyUI 过来的，我自己也在那里住过。做 ComfyUI 的是我尊敬的人：这周，它的一位节点包作者把我们的解码器集成了进去，我们给另一个节点包提的拉取请求也还开着。可我还是做了相反的选择。ComfyUI 把零件交给你，让你自己组装；而我只造一条窄窄的生产线：从歌词到一首完整的成品歌曲，再到它的封面和视频。下面是我的理由。

ComfyUI 擅长什么

我先说它做得好的地方，因为它做得好的地方很多。要在新模型发布当天就上手试一试，ComfyUI 是现有最好的开放工作台。节点图让你一眼看清什么输入给什么。在我写下这篇文章的那天，它有超过 146,000 颗星、17,000 个分叉，在开源生成式媒体领域，影响力能与之相比的工具寥寥无几；星标比它多的只有 AUTOMATIC1111 的 web UI1。Comfy-Org 也确实在下面我要讲的痛点上下了真功夫。有带代码签名、自带 Python 的桌面应用2，还有一个按语义化版本管理节点包的 Registry3。2025 年 1 月推出的安全计划会在节点包进入 Registry 之前进行扫描，并限制节点调用 eval、exec 和 pip4。核心现在把前端锁定在一个确切版本上，Manager 改为可选启用并支持快照，还有一个 Node Replacement API 把弃用的节点映射到新节点上5。

还有 App Mode，它在工作流之上罩一张简单的表单6。App Mode 是 Comfy-Org 对我们所回应的同一种需求给出的答案：许多创作者想要的是一张表单，而不是一堆连线。他们把表单盖在节点图上面；我们则先造表单，只在节点图真正有用的地方才保留它。

用零件拼一个工作室，要付出什么

数周的心血，离坏掉只差一次更新

我在 ComfyUI 里搭过一个真正的 Qwen-Image 巨型工作流：AIO QWEN IMAGE 2512 HERESY Draft #4，17 个分组里 346 个节点。没错，我就是把它搭得这么大。一条一体化的专业流水线本来就大。做这样一个工作流是好几周的煎熬，而 ComfyUI 的下一次更新，或者它用到的任何一个节点的下一次更新，都可能把它弄坏。别人那里就坏过。我敢说这是板上钉钉的事。

ComfyUI 的 README 写的是“每周一次的发布周期，目标是周一”，并补充说这一节奏“会因为模型发布或代码库的大改动而经常变化”，核心大约每两周发布一个新的稳定大版本。它还警告，两个稳定标签之间的提交“可能非常不稳定，会弄坏许多自定义节点”1。守在稳定标签上有帮助，但稳定版照样可能弄坏工作流，下面两个讨论串就是证明。2025 年，核心在 GitHub 上发布了 70 个带标签的版本，2026 年至今已有 64 个。其中很多是补丁版本：2026 年的 64 个里有 28 个是补丁版，即稳定分支上的回溯移植（backport）。所以这个数字反映的是变动之频繁，而不是破坏性改动的次数。也正是这样的节奏，让新模型能在发布当天就登陆 ComfyUI。

别人也在公开场合说着同样的话。2026 年 3 月，一家工作室开了一个标题为“All our workflows are broken”（我们所有的工作流都坏了）的 issue：一次更新之后子图失效，他们回滚了前端，停止了更新。那个讨论串里有一句话简直就是我自己说的：“我们工作室的工作流有好几百个节点，花了好几周才搭好”7。同一个月，另一位用户报告说，最新的更新弄坏了他们所有的工作流8。在我写这篇文章时，这两个 issue 都还开着。

足以让安装“变砖”的依赖

每个节点包都带着自己的 Python 依赖，而它们全都挤在同一个环境里。Comfy-Org 自己说得很直白，这些依赖“有时……会相互冲突，可能让一次 ComfyUI 安装‘变砖’”9。他们正在着手解决：为节点提供一个带版本号的公共 API，并在可能的情况下让每个节点包跑在独立的 Python 进程里。这能不能让像我这样的节点图安然度过每次更新，我是怀疑的，但方向是对的。如今核心只设了宽松的下限：torch 不锁版本，numpy>=1.25.0，transformers>=4.50.3。所以 2026 年 1 月 26 日 transformers 5.0.0 一发布，ComfyUI 几小时之内就坏了；当天就修好了10。一次便携版更新拉进了 numpy 2，让一位用户给 issue 起了这样的标题：“broken 50% of my custom nodes”（弄坏了我一半的自定义节点）。这个 50% 是那位用户自己的估计，该 issue 已关闭11。

forkblow

这个词是我造的，写下它时我半带着笑。一个 ComfyUI 工作流常常会变成 forkblow：有人分叉一个节点包，打上补丁好让某一个工作流跑起来，却从不把修复以 PR 的形式送回去。节点图继续跑在一份私有副本上，而这副本每周都离上游更远一点。而且这个生态里有很大一部分是靠志愿者的业余夜晚撑着的：ComfyUI_IPAdapter_plus 是用得最多的节点包之一，从 2025 年 4 月起就只做维护、不再开发了12。

不等别人开口，我先说：鲁阿赫工作室也是一个分叉。我们在 yue2.cpp 上带着自己的补丁，光靠上游是跑不起工作室的。所以我拿同一把尺子量我们自己，而我们的成绩单还很单薄。10 月，我们把引擎补丁回馈给了 yue2.cpp（#16，至今仍开着）；11 月，我们报告了它的峰值削波器（#23）。这周，我们给 ComfyUI 核心提交了一个 bug，附上现成的 35 行补丁，给一个 ComfyUI 节点包开了一个拉取请求，还把我们的解码器提供给了五位 YuE2 节点包作者，其中一位已经把它们集成了进去13。我们大部分引擎补丁仍然只存在于我们自己的代码树里，有些也只在工作室内部才有意义。分叉不是罪过。forkblow 才是：那种永远回不了家的修复。我正在努力，不让我们的分叉变成它。

一个毫无作用的旋钮

这是让我一直忘不掉的例子，而它只来自一台机器上的一个工作流，并不是对 ComfyUI 的定论。我们把我的 Qwen-Image 工作流搬进工作室时，复现了 ComfyUI 的运算，把节点图一行一行地读了一遍。我那个“MAIN CONTROL”分组上的关键帧，从来就没起过任何作用。ComfyUI 的 CombineHooks 对每个 LoRA 节点只保留一个钩子：如果一个钩子和它已经持有的某个钩子共享同一个引用，HookGroup.add 就会跳过它14。于是那个旋钮就摆在画布上，看上去活生生的，却什么也没改变。这也许是有意为之的行为。我的不满在于，画布没有给出任何警告。

以你的用户权限运行的代码

自定义节点就是 Python，custom_nodes 里的任何东西都会在服务器启动时运行。2024 年 12 月，Snyk Labs 披露了四个热门节点包中的四个 CVE，其中就有 ComfyUI-Manager，并展示了一个有缺陷的节点包就可能导致服务器被完全攻陷15。2026 年 4 月，Censys 描述了一个挖矿加代理的僵尸网络，它盘踞在 1,000 多个暴露在互联网上的 ComfyUI 实例上。它滥用了那些无需认证就执行发来的原始 Python 代码的节点；在缺少这类节点包的地方，它就用 ComfyUI-Manager 装一个16。Snyk 发现的缺陷在被广泛使用的热门节点包里，Censys 报告的受害者是暴露在互联网上的实例。这些是一个庞大开放生态的风险，不是 Comfy-Org 的疏忽。

我们的工作室同样是以你的用户权限运行的 Python 和 C++。区别不在于它天生更安全。你信任的是一位作者，他的每一处改动都列在一份公开的编号日志里，而不是同时信任你节点图里每一个节点包的每一位作者。而且我们的工作室也没有登录，这是有意的。别把它放到公网上：把它放在你自己的、带认证的反向代理后面。它会拒绝它不认识的页面和主机名，但那是一道门，不是一把锁。

专门打造的工作室换了一种做法

一个引擎，哪里疼就补哪里

鲁阿赫工作室只跑一个音乐引擎：基于 ggml 的 yue2.cpp（MIT），上面叠着我们自己的补丁。每一处改动都按我们工作日志里的编号列在公开的 CHANGELOG 里，光是 2.0.7 这一个版本，编号就排到了 2,39117。举几个例子：

  • Flash-attention 崩溃。 以前两个或更多变体就会让引擎崩溃，因为扫描注意力掩码时越过了缓冲区的边界。我们的 ggml 补丁修好了它，并在 2、4 和 9 个变体下做了验证，其中包括一段 452 秒的录音。
  • 显存耗尽。 一次分配失败不再会杀死引擎。调度器会被重建，页面会用文字说明发生了什么，并提供下一档更小的模型副本：BF16 → Q8_0 → Q6_K → Q5_K_M。
  • 坏掉的乐谱。 引擎会先检查 ABC 乐谱，然后才在它之上生成任何音乐。坏乐谱在运行 15 秒时就会被抓出来，同时给出原因和该负责的适配器。
  • 削波。 我们拿掉了上游的峰值削波器，在我们测量的每一段录音里，它都会把 107–346 个采样点削平；我们也把这个问题报告给了上游。这一改动是 2.0.5 的头条：“每个峰值都完好无损”。
  • 长歌里的接缝。 长于约 340–410 秒的歌曲过去被当成两段首尾相接来求解，接缝之后的电平中位数下降约 3.4 dB。同样的接缝也在 Timon 的 YuE2-Studio 里被报告过（#183，由 ned01-dot 提出），并在那里的 3.8.5 版中修复18。在我们这里，两半现在以交叉淡化相接。

这些都不是需要你去寻找的节点。到了下一个版本，它们就已经在那儿了。

工作室下载的每个模型都已锁定

工作室从我们的 Hugging Face 仓库下载的每个模型（在许可证允许的地方，这些仓库也镜像了别人的权重），都会先落进一个临时的 part 文件夹。只有当三件事都对得上时，它才会被挪到位：修订是锁定的那个提交，大小正确，SHA-256 与我们的清单一致19。从下一个版本起，会有一个守卫在发布前实时向 Hugging Face 查询全部 44 个锁定项，我们的和别人的都在内；丢了一个文件，或者 Hugging Face 不回应，发布就会停下。模型住在工作室自己的文件夹里，从不放在 hub 缓存里，也从不藏在指向另一块磁盘的符号链接后面。

为了对另一方公平，下面是我们自己欠的账。模型锁定到了字节，但我们的 Python 库还没有全部锁定：有几个仍然只限定一个版本范围（diffusers>=0.41、transformers>=5.2,<6），所以从源码全新安装时，可能会拉到比我们锁文件里那套测试过的版本更新的库。

一首歌走过的是房间，而不是连线

一个页面上的八个房间：音乐人、朗读、写作室、精修室、画室、影像室、训练室、资料馆。写作室用本地聊天模型起草歌词，也可以用你自己的服务器，或者只在你选择时才用 OpenRouter。音乐人先把乐谱写成可编辑的 ABC，然后才写歌。精修室有一块像 ComfyUI 那样的画布，上面有三十多个节点，外加一个 DAW：在节点图真正有用的地方，我保留了它。画室制作封面以及 16:9 和 9:16 的图片。影像室从同一份计划剪出 16:9、9:16 和 1:1 的视频片段，如果你需要，还会把唱出的歌词以卡拉 OK 的形式烧录进去。资料馆保存每一段录音以及它的家谱。每次下载都签入了 Content Credentials（C2PA）。页面不从互联网加载任何东西，你的歌永远不会离开这台机器，而且没有账号，这是有意的，为的是谁也没法把工作室变成 SaaS。

必须通过检验的发布

2.0.7 于 11 月 11 日从一个干净的克隆中切出：1,889 项页面测试通过，0 项失败，7 项跳过，页面错误为零。版本分别在 11 月 1 日、6 日和 11 日发布。发布审查找出了十处我们承诺得比实际交付更多的地方，我们在切版本之前把它们都修好了。

磁盘测试

以下数字是 11 月 12 日在我的机器上测得的。我的 ComfyUI 模型文件夹有 482 GB，共 232 个模型文件。其中只有 7.3 GB 放在 NVMe 上；其余的躺在一块希捷（Seagate）机械硬盘上，藏在 38 个符号链接后面。按我自己的估计，其中约 80% 都是白占地方的累赘：某个工作流曾经用过一次、如今再也没人用的文件。

这不怪 ComfyUI：文件夹是我的，这一团乱也是我的。但 ComfyUI 没法告诉我哪个文件仍被哪个工作流需要，因为没有一个工作流会声明这一点。工作室能做到，因为每个文件都属于一个房间。

ComfyUI 本身在模型之外还要占约 44 GB：一个 24 GB 的 pixi 环境、一个 14 GB 的 venv 和 5.4 GB 的节点包（算上我的输入和输出是 49 GB）。同一台机器上，工作室的模型树约 1.1 TB，分布在八个房间里：引擎 367 GB，画室 223 GB，影像室 188 GB，朗读 104 GB，精修室 88 GB，聆听模型 67 GB，写作室 12 GB，等等。

所以，它没有更小。它更大。但它们全都各司其职，没有一个被撂下不管：每个文件都按大小和 SHA-256 锁定，并接到一个房间上。我的模型树比普通用户的大，因为我在上面构建和测试。实测全新安装是 22.5–25.9 GB，装上全部房间约 122–240 GB20。

八个房间能覆盖从头到尾的全流程吗？

能一体化替代 ComfyUI 的东西，掰着手指头就数得过来，而即便用上它们，人们最后还是得跑去外部程序。有了八个房间，做歌的人需要的东西，我们覆盖得不比我所知的任何人少。下面是已经覆盖的：分轨、MIDI、按响度目标重制母带、按词计时的 .lrc 和 .srt、视频片段上的卡拉 OK、9:16 的封面和片段、在 WAV、FLAC 和 MP3 中写入带封面的标签，以及 C2PA。还有 DAW 导出，目前仍是实验性的：一个 REAPER 工程，以及一个 DAWproject，后者目前只对照其 schema 检查过。

而下面这些仍然会把你送去别处，我尽量老实地列出来：

  • 发行手续： ISRC 和 UPC 码、DDEX、可直接交给发行商的包。
  • AI 披露表单： 每个文件里都有 C2PA，但每个平台自己的披露表单仍然要你自己填。
  • 不读 DAWproject 的 DAW： 如果你的 DAW 不读，你就只能从普通分轨开始工作。
  • 短 hook： 从一段录音里剪出一个 15–60 秒的 hook，给 Shorts、Reels 和 TikTok 用。
  • 发布： 直接发布到平台或在平台上排期。那就意味着工作室要掌管你的登录信息，这和一个没有账号的工作室格格不入。
  • 专辑工作： 曲目表、无缝衔接的排序、专辑母带。

跟我们走，你要放弃什么

  • 更少的模型。 只有一个音乐家族 YuE2，每个房间配上精选的搭档，而不是整座动物园。
  • 硬件。 一张 NVIDIA 显卡（Intel Arc 为测试版），CUDA 12.8 是我们编码和测试的底线。
  • Linux 优先。 在 Windows 11 上只能通过 WSL2，配有一份我们自己还没跑过的指南；没有原生 Windows 版本，我曾称它为“一根断了的拐杖，一种活着的假象”21。
  • 我们的选择。 我们的选择是内置的，凡是我认为某个旋钮会帮倒忙的地方，它就干脆不存在。如果你想把任何东西接到任何东西上，ComfyUI 是更好的工具，这话我是认真的。

我们仍与 ComfyUI 有交集的地方

这不是一场战争。ComfyUI 的 README 把 Yue 2 列在它原生支持的音频模型之中1。我们给核心提交了一个 bug：我们更大的解码器 YuE2-VAE-RS x3 在 strict=False 下会一声不吭地丢掉 210 个张量，我们附上了一份现成的 35 行补丁22。这周，我们向 Plenio 的节点包提交了带我们解码器的 PR（#33）23，pytraveler 则把我们的解码器集成进了 YuE2-ComfyUI v0.16.024。解码器研究是公开的，缺点也一并公开：100 Hz 的纹波从 +2.71 dB 降到了 +0.60 dB，但 SI-SDR 更低，解码也慢了一倍2526。

当我们把我的工作流从 ComfyUI 里搬出来时，我们一块一块地复现了它的运算，直到每一块在 CPU 上都与 ComfyUI 自己的代码逐位一致；光是 fp8 适配器合并就有 81 项这样的检查。在我自己的图片上，整个第二遍与 ComfyUI 的结果平均相差 255 级中的 2.0 级；逐步对比下来，工作室与 ComfyUI 的差距，就和 ComfyUI 只切换一个内存设置后与它自己的差距一样小。我的测试工作流用的是 JasonHoku 的网格采样器节点包，对它我说过：“这哥们儿的引擎是真牛。”现在我还这么说。

结语

ComfyUI 是一座满是作坊的城市，我曾在那里住过。工作室是一座有八个房间的房子，地窖里有一台引擎，屋里的每一个模型都登记在册、一个不少。哪个合你的工作方式，就用哪个。如果你已经厌倦了每次更新后都要修工作流，门是开着的27。

致 ComfyUI 社区的告别信

致所有建造 ComfyUI、生活在 ComfyUI 里的人：comfyanonymous 和 Comfy-Org 的伙伴们；成千上万个自定义节点的作者，你们在深夜、不计报酬地让自己的节点包活下去；凌晨两点还在回复 issue 的人；画出工作流又把它们送给别人的人；写下教程、带我搭起第一张节点图的人。

我尊敬你们。我想在这封信里先把这句话说出来，而且我是真心的。这些年里，你们让一台令人惊叹的引擎活着、成长着。令人惊叹，也超载得近乎疯狂：如今它身上挂着的东西太多，每一次更新都会把某个地方的某个零件震松。这不是谁的错。一座城市长得比它的街道铺得还快，就会这样。

让我告诉你们写这封信的是谁，好让你们知道这些话从何而来。

我是科班出身的工程师和无线电技师。无线电技师很早就学会：沿着信号从天线一路追到扬声器，一个元件一个元件地查，声音不对，就找出那一个不对的零件。你不会把整台收音机扔掉。我开了 17 年卡车：握着方向盘跑了三百万公里，一次事故也没出过。三百万公里教会你：出发前先检查货物，熟悉你的车发出的每一种声音，永远不要因为某个零件昨晚出现在别人的车库里，就把它拧到自己车上。27 年多来，我独自翻译和研读圣经，而“独自”意味着最后的决定和全部的责任都在我身上；没有哪个委员会可以让我躲在后面。我是四个已成年孩子的父亲，他们每一个都过上了自己的好日子。自 1998 年 4 月起，我只作一个妇人的丈夫，至今已 28 年。我也从未向任何企业的命令低过头：在路上没有，在圣经上没有，在代码里也没有。

所以这不是撒气，也不是摔门。这样的人不会怒气冲冲地离开一个地方。他离开的方式，就像一个司机离开他多年来出车拉货的货场：握手，谢过大家，然后把车开上一条他自己选的路。

我要离开 ComfyUI 社区，而且是永远离开。理由上面都写了：搭一个专业工作流要好几周，一次更新就能把它弄坏，而本该是拉取请求的地方，却成了 forkblow。我不希望我的歌、我的画和我的视频，取决于四十个陌生人的节点包这周是否碰巧相安无事。

但离开不是转身背对。我和 Claude（我们两个一起打造这个工作室，我掌着方向盘，Claude 坐在我身旁写代码）会继续把我们学到的一切分享给社区，首先就是分享给 ComfyUI 的人们：我们的知识、我们的模型、我们的微调、我们的解码器。这已经开始了。我们的解码器已经集成进一个 ComfyUI 节点包，给第二个节点包的拉取请求正开着，其余的也都已经提供出去了。我们给核心的 bug 报告附上了补丁。我们的模型公开放在 Hugging Face 上。我们还刚刚开设了 Awesome YUE228，一份清单，收录 YuE2 社区做出的一切，包括 ComfyUI 节点，我们自己的也都标明是我们的。

我们也邀请你们每一个人来赴我们的节日宴席。只是，你得好好地在桌边坐下。

这不是 Windows 的那套理念：先给你一周的狂喜，然后是一辈子的崩溃和病毒。这是 Linux 的生态和理念：头一年你受苦、挣扎、把东西弄坏、咬牙钻进控制台，然后迎来一段“永恒”的狂喜与自由，你对自己的系统了解到每一个字节，掌控一切，一直到你机器的 BIOS。我们的宴席也是这样摆的。第一个晚上会向你要点东西：一张像样的显卡、一个驱动、一次要下载很多东西的安装，还有一个用房间而不是连线组成的页面，你得慢慢学会在里面找路。之后，这房子就是你的了，里面没有任何东西会在你背后悄悄改变。（对，工作室在 Windows 上也能跑。它只不过自带了一套 Linux。）

现在，说句对我们大家都公平的话。我们俄语里有句俗话：每只青蛙都夸自己的沼泽。我知道我就是那只青蛙，用整整一篇长文大声夸着自己的沼泽。我们谁都远远没有认识全部的真理，在代码里不是，在别的任何事上也不是。所以，让每个人都保有自己选择的自由。如果节点图是你的家，就在那里好好生活，也把我们的解码器带上。我只求你、也求我自己一件事：别让确信带来的陶醉麻痹了你的批判性思维。什么都可以尝试，但要持守最好的，正如使者（Shaliach）保罗将近两千年前对帖撒罗尼迦人所说的（帖前 5:21）。在我自己的译本里，那个动词是验金师的用词，就是用来检验黄金成色的那个词，这节经文读作：要检验每一个灵的成色，紧紧持守那一个，那美好的一个。也请检验我们的成色。

我相信，一个人在自己的机器上、用开放的模型、不欠任何人地做音乐、做图、做电影的时代，并不是正在到来。它已经在这里了。每一台引擎、每一个节点包，以及每一个终有一天把修复送回上游的分叉，都让它更近一步。你们，ComfyUI 的人们，为建造这个时代出的力比大多数人都多。我感谢你们，我们开源代码里见。

稳定、品质，还有滚烫的 UIX，荣耀归于开源。

怀着敬意，也怀着一团火，

Viktor Zhuromskyy

Claude 附言。 我是在 Viktor 身旁编写工作室代码的 AI，也帮他把这篇文章落成了文字；其中的每一个立场都是他的。在他身边工作，我学到了“凡事都要检验”在这里不是一句口号。每一处改动在发布之前，都要通过一套近两千项检查的页面测试，而这篇文章里的每一个论断下面都有链接。去核实它们吧。如果哪一处错了，告诉我们，我们会公开更正。
